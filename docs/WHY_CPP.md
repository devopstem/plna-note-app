# Почему карта на C++, а не целиком на Kotlin

Короткий ответ для демо и ревью: **Kotlin отвечает за продукт (экраны, списки, офлайн, датчики). C++ отвечает за геометрию зала и маршрут — один раз, для всех платформ PLNA.**

---

## Разделение труда

| Задача | Где | Почему |
|--------|-----|--------|
| Список покупок, Material UI, Room, язык | **Kotlin** | Это Android-продукт; здесь Jetpack сильнее |
| PDR (шаги, компас) | **Kotlin** | SensorManager / разрешения — родные API Android |
| План зала в метрах, стеллажи, маршрут, draw-list | **C++23 `plna_core`** | Общее ядро экосистемы PLNA |
| Рисование на экране | **Kotlin `StoreMapView`** | Берёт готовый `float[]`, не считает геометрию |

```
     Kotlin «оболочка»                    C++ «двигатель»
  ┌─────────────────────┐              ┌─────────────────────┐
  │ UI · списки · Room  │   JNI JSON   │ MapScene (метры)    │
  │ PDR · жесты камеры  │ ───────────► │ route · draw list   │
  │ Canvas / paint      │ ◄─────────── │ opcodes → float[]   │
  └─────────────────────┘   float[]    └─────────────────────┘
```

---

## Зачем не «всё на Kotlin»

1. **Один алгоритм — несколько клиентов**  
   Тот же `plna_core` рассчитан на Android (сейчас), затем iOS / desktop / CI без переписывания маршрута и парсера плана. На чистом Kotlin пришлось бы дублировать геометрию в Swift/C#.

2. **Realtime без GC-сюрпризов**  
   При pan/zoom карта часто пересобирает draw-list. Нативный код предсказуемее по latency и не конкурирует с UI-потоком за паузы сборщика мусора так же, как тяжёлый Kotlin-цикл каждый кадр.

3. **Общая модель с PLNA**  
   Планограмма (`store_maps`), маркеры входа/касс, единицы в метрах — контракт ядра. Приложение Android — тонкий host, не «вторая правда» о зале.

4. **Тестируемость ядра без эмулятора**  
   Core собирается CMake’ом отдельно; desktop/CI может гонять геометрию без полной Android-сборки (см. `app/src/main/cpp/`).

---

## Зачем тогда Kotlin вообще

Потому что **продукт — это не только карта**:

- заметки, количество, офлайн Room, Firebase sync;
- Material 3, локали ru/en/be, тема;
- история покупок, permission UX, PDR на датчиках телефона.

Писать всё это в C++ было бы дороже и хуже для Android UX. JNI — узкий мост: загрузили JSON зала → получили draw-list и маршрут.

---

## Аналогия

```
Kotlin  =  приложение-навигатор (экраны, список адресов, GPS-разрешения)
C++     =  движок карты (тайлы/вектор, маршрут по графу)
```

Мы не «убегаем от Kotlin» — мы **не дублируем планограмму** в UI-слое.
